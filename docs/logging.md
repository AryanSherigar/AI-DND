# Logging policy

Structured JSON logging, configured in `app/logging_config.py` (independently
duplicated in `apps/core-api` and `apps/turn-resolution-service` — no shared
Python package exists between the two services). All logs currently go to
stdout only; no aggregator/sink is wired up yet, but the log shape is
GCP-Cloud-Logging-compatible (`timestamp`, `severity`, `jsonPayload` fields)
so plugging one in later needs no schema changes.

## Retention (intended, once a sink exists)

- `operational` category logs (default): **30 days**.
- `audit` category logs (`event_category=audit` — publish, playthrough start,
  share link creation, etc.): **1 year**, in a separate log bucket/sink
  filtered on `jsonPayload.event_category="audit"`.

Not enforced yet — these are target values for whichever GCP log bucket
config (or equivalent) is eventually set up.

## Sampling for high-volume events

There is no per-chunk SSE narration logging at all — only an aggregate
`gemini_call_completed` event with `chunk_count` and `duration_ms`, logged
once per Gemini call. This is "don't log the high-volume tier," not
probabilistic sampling: per-chunk data isn't individually actionable, and the
aggregate is what debugging actually needs. If per-chunk debugging is ever
needed, gate it behind `LOG_LEVEL=DEBUG` rather than adding a new sample-rate
config.

## Redaction

`redact_sensitive_fields` (a structlog processor, not a call-site convention)
strips any field whose name matches a fixed denylist — tokens, API keys,
passwords, email, display name, and Gemini prompt/narration content — before
a log line is rendered, regardless of call site. See `REDACTED_FIELD_NAMES`
in `logging_config.py` for the exact list.

**IP addresses are not logged at all** in this pass. This is a deliberate
scope decision, not an oversight: hashing would need salt management with no
current consumer, and nothing today needs geographic/abuse analysis. Revisit
if rate-limiting or abuse detection becomes a requirement.

## Correlation IDs

`X-Request-Id` is generated by the frontend per user action (not per page
load, and not by core-api) and propagated through both `apps/core-api` and
`apps/turn-resolution-service` via `request_context.py` middleware, bound as
a structlog contextvar for the lifetime of the request. See each service's
`app/middleware/request_context.py`.
